# EDT-101 — Help and Maximize buttons next to the close button

Status: **approved** (human, 2026-11-18) · Owner: skate-editor · Deps: EDT-88 · Priority: P1

## Problem

From the human (Discord, 2026-11-17): the `?` button sometimes sits alone on its own row and wastes space.

Every standard window draws a header row (`WindowHeader.render`, EDT-51 §2.2 / EDT-67): the window's own tools on the
left, then Maximize (EDT-88) and `?` at the right end. When a window has no tools, the row holds only those two
buttons:

- Properties;
- Audio Inspector;
- Animation Editor;
- Animator;
- Video to Animation;
- Asset Store;
- every dialog (`EditorDialog`);
- Hierarchy, Project and Version Control while they have nothing to show (no scene, no project, no repository).

The task asks for the two buttons in the title bar or tab, next to the close button, "if ImGui docking allows",
with a short note if that needs custom drawing. It does, for docked windows.

## What ImGui 1.90 allows

| Where the window is | Title bar / tab | Buttons there |
|---|---|---|
| **Floating** (dialogs, undocked windows) | The title bar belongs to the window itself. | Normal widgets work. Draw them at the title bar's right end, left of the X, with the clip rect widened to the title bar. Hover and click reach them because the mouse is over our window, and pressing an item there does not start a window move. No custom input. |
| **Docked** | The tab bar belongs to the dock node's **host** window, not ours. | Widgets submitted from our window at tab-bar positions never get hover or clicks: ImGui routes the mouse to the host. They would have to be drawn on the host's draw list and hit-tested by hand (`isMouseHoveringRect` / `isMouseClicked`). |
| Docked, tab bar hidden | The Game Viewport's auto-hidden node (EDT-88), or a node a user set to hide its tab bar. | Nowhere to put them. |

Other limits of the docked case:

- **ImGui cannot reserve room in a node's tab bar.** There is no API to shrink the tabs, so with many tabs, or a
  narrow node, our icons would sit on top of the last tabs. We would have to skip drawing them when the tab bar has
  no free room, which we can only estimate from the tab widths.
- **Pressing on empty tab-bar space starts a node drag.** A hand-made button there must swallow the mouse-down before
  ImGui sees it, which means setting the active ID ourselves (internal API) or accepting that a press-and-drag on our
  icon undocks the window.
- **Every dock layout state needs a test:** one tab, many tabs, narrow, floating, maximized (EDT-88), hidden tab bar.

## Options

**A. Title bar for floating windows, custom icons in the tab bar for docked ones.**

- Floating: real buttons in the title bar.
- Docked: `?` and Maximize drawn at the tab bar's right end (left of the node's close button), hit-tested by hand,
  and only when the tab bar has room. Otherwise they go back to the content row (option C).
- Closest to what was asked, but the docked half is custom input on ImGui internals, with the risks above.
  Start with a headless spike (draw, click, drag, many tabs).

**B. Title bar for floating windows; docked windows keep the buttons in the content, never alone.**

- Floating: as in A.
- Docked, with tools: tools, Maximize and `?` share one row, as today.
- Docked, no tools: the row is removed. Maximize and `?` are drawn over the top-right corner of the content, and
  only the first line's width is reduced by the buttons' width (a `pushTextWrapPos` / item-width limit for that one
  line). Help and Maximize also stay in the tab's right-click menu (EDT-51, EDT-88).

**C. No visible buttons on docked windows without tools.**

- Floating: as in A.
- Docked, with tools: the buttons stay on the tools row.
- Docked, no tools: no header row. Help and Maximize are in the tab's right-click menu (already there), plus a tab
  double-click (Maximize) and F1 (Help, new).
- Cheapest, but the `?` is no longer visible on those windows.

## Recommendation

**B.** It removes every row with only `?` on it, puts the buttons next to the X on every floating window and dialog
with plain widgets, and needs no input hacks on dock nodes. A is possible but fragile: tab overlap, drag-to-undock
on press, and internal APIs. If A is preferred, it starts with the spike, and B's content-row placement is its
fallback.

## Work plan for B (one commit each, with tests)

1. **Floating windows and dialogs:** `WindowHeader.titleBarButtons` draws Maximize (when `canMaximize`) and `?` in
   the title bar, left of the close button. The dialog `?` row (`helpRow`) goes away.
   - Tests (headless ImGui): both buttons sit inside the title bar, left of the X, are hit by a simulated click, and
     a click does not move the window. `HelpButtonClipTest` is extended to the title-bar placement at every density
     and scale.
2. **Docked windows without tools:** the buttons go over the top-right of the content, and the first line is limited
   to the width beside them.
   - Tests: no window draws a row holding only the header buttons (a guard over every registered window); the first
     content line never overlaps the buttons; the narrow-dock guard (EDT-100) still passes.
3. **Docked windows with tools:** unchanged, except the row never wraps the buttons alone. When the tools do not
   fit, they shrink first (EDT-86 `TrailingButtons`).

## Open questions

1. **A, B or C?** Recommend **B**.
2. **F1 for Help on the focused window?** Recommend **yes**: rebindable, ignored while typing, like Shift+Space for
   Maximize (EDT-88).

## Decisions (approved 2026-11-18)

1. **Option B:**
   - floating windows and dialogs: Maximize and `?` in the title bar, next to the close button;
   - docked windows with tools: the buttons stay on the tools row;
   - docked windows without tools: the buttons sit over the top-right corner of the content.

   The buttons are never alone on a row.
2. **F1:** yes, a rebindable F1 opens Help for the focused window, ignored while typing.
