# QA-04 — Industry-standards audit

Method: static scan of `src/main/kotlin` (grep + reading), headless from WSL. Nothing was run on a GL/AL context, so GPU/audio leaks are
inferred from the absence of delete/destroy calls and should be confirmed with a debug-context run. Counts are as of this branch.
Priority: P1 = fix soon, P2 = plan, P3 = nice to have. Owner = domain prefix.

## Summary

| Area | Status | Headline |
|---|---|---|
| Resource lifetimes | Weak | No `AutoCloseable`/`Closeable` anywhere; 45 ad-hoc `destroy`/`cleanup`/`dispose` methods; several GL owners never delete their objects |
| Logging | Partial | 34 `println`/`printStackTrace` calls bypass `LoggerService` |
| Error handling | Partial | Many broad `catch (e: Exception)`, `runCatching` swallowing errors (e.g. `ViewportRenderer.captureScreenshot`) |

| Frame allocations | Watch | ~78 candidate per-frame allocations in `engine/render/renderer` and `engine/ecs/systems` |
| Units / coordinates | Undocumented | Mix of degrees (editor/Transform) and radians (JOML/physics); no written convention |
| Config / versioning | Weak | No schema version in scene/asset/material JSON; hard-coded developer paths |

## 1. Resource lifetimes (`AutoCloseable` / dispose)

Findings:
- No type implements `AutoCloseable`/`Closeable`; lifecycle is a convention of per-class `destroy()`/`cleanup()` (`Renderer`, `Renderer2D`,
  `ShadowRenderer`, `SkyDomeRenderer`, `SkyboxRenderer`, `SplashRenderer`, `TextureRenderer3D`, `ThumbnailRenderer`, `RenderPass.cleanup`).
  Nothing enforces that they are called, and `use {}` is impossible.
- GL objects created with no matching delete in the same class:
  - `assets/data/CubeMap.kt` — `glGenTextures`, no `glDeleteTextures`.
  - `assets/loaders/TextureLoader.kt` — textures created per load; deletion depends on callers (no owner type for a texture's GL id).
  - `render/renderer/DebugRenderer.kt` and `PickingRenderer.kt` — create VAO/VBOs (`glGenVertexArrays`/`glGenBuffers`) but have no `destroy()`.
  - `ThumbnailRenderer.glGenTextures` hands the id to the caller ("must eventually delete"), with no wrapper type.
  - `ShaderLoader` is fine (shader/program ids are owned by `Shader`, which deletes them).
- `JobSystem` owns a `SupervisorJob`/`CoroutineScope`; confirm `Engine.destroy()` cancels it (it destroys screens, renderer, scenes, systems only).
- `Engine.destroy()` returns early unless state is `RUNNING`, so a failed/loading engine leaks audio and native resources.
- `AudioEngine`/`SoundSource` are OpenAL handles with no `Closeable`.

Follow-ups:
- REN (P1): introduce a small `GpuResource : AutoCloseable` base (id + `close()` + idempotent) for textures, buffers, VAOs, FBOs; make `CubeMap`, `DebugRenderer`, `PickingRenderer` own and free theirs.
- AST (P2): `AssetsManager` should own texture/mesh/sound lifetimes and delete on unload.
- AUD (P2): make `AudioEngine`/`SoundSource` `AutoCloseable`.
- ECS (P2): `Engine.destroy()` should always release what was created, and cancel `JobSystem`.
- QA (P2): architecture guard "every class that calls `glGen*`/`alGen*` has a delete" (QA-05).

## 2. Logging

- `LoggerService` is the sanctioned sink (`log`, `logEditor`, `logGame`). 34 calls bypass it. Worst offenders:
  `AssimpExtensions.kt` (9), `ShaderLoader.kt` (8), `GameMain.kt`, `Window.kt`, `JobSystem.kt`, `EventSystem.kt`, `SearchHistory.kt`,
  `TranslateGizmo.kt` (2 each), plus `NativeLibraryLoader`, `StringManager`, `SoundLoader`, `EngineExtensions`, `SearchEngine`, `imgui/components/Component.kt`, `LoggerService` itself.
  Shader compile errors in `ShaderLoader` (the most useful diagnostics) therefore never reach the editor console.
- `printStackTrace()` in catch blocks loses structured context (`StringManager.loadStrings`, `EventSystem`, `JobSystem`).
- `engine/utils/testing` contains debug `println`s (excluded from the count; should not ship in main).

Follow-ups: AST (`AssimpExtensions`, `ShaderLoader`, `SoundLoader`), ECS (`Window`, `JobSystem`, `EventSystem`, `StringManager`, `LoggerService` fallback), EDT (`SearchHistory`, `SearchEngine`, `TranslateGizmo`, `Component.kt`), GPL (`GameMain`). QA adds a `no println` guard once these are fixed (QA-05).

## 3. Error handling

- Broad `catch (e: Exception)` is the norm; failures are logged as strings (or only `printStackTrace`) and callers get `false`/`null` with no reason (`StringManager.loadStrings`, loaders).
- `runCatching { ... }` swallows everything with no log (`ViewportRenderer.captureScreenshot`) — a screenshot failure is invisible.
- Event/job callbacks: `EventSystem` and `JobSystem` catch handler exceptions (good) but only print them.
- Commands expose `wasSuccessful()`/`getFailureReason()` for file commands (good pattern) but it is not universal.

Follow-ups: ECS (P1) — route handler/job exceptions through `LoggerService.log(..., ERROR)` with the exception; AST (P2) — return a `Result`/sealed outcome from loaders instead of `Boolean`/`null`; EDT (P2) — log in `captureScreenshot`.

## 4. Thread-safety of shared state

- Good: `UndoRedoManager` (history lock), `AssetsManager`/`AssetRegistry` (concurrent maps/locks), `JobSystem` main-thread queue (concurrent queue + per-frame budget, tested by `JobSystemUpdateBudgetTest`), `Engine.engineState` (`AtomicReference`).
- Risks:
  - `Engine.runtimePlaying`, `Engine.screens`, `Scene.children` and `EventSystem` subscriber lists are plain mutable state; async jobs (`runAsync`/`runIO`) that touch them can race with the main loop. Convention should be: async work never mutates scene/engine state, it posts via `runOnMain`.
  - `LoggerService` is called from jobs and the render loop; confirm its buffer is thread-safe.
  - `mainThreadId` is captured in the `JobSystem` constructor, so `JobSystem` must be created on the main thread (true today in `Engine`, not asserted).
  - `Thread.currentThread().id` is deprecated on newer JDKs (`threadId()`); fine on JVM 17.

Follow-ups: ECS (P1) — document and assert "scene/engine mutation on main thread only", make `EventSystem` subscription list copy-on-write; ECS (P2) — make `LoggerService` thread-safe if it is not.

## 5. Frame-allocation hotspots

About 78 constructor/collection allocations in `engine/render/renderer` and `engine/ecs/systems` are not simple field initialisers (JOML `Vector3f()`/`Matrix4f()`, `listOf`, `FloatArray`). Examples already seen in per-frame paths:
- `RagdollSystem.update` allocates `Matrix4f(goTransform.worldMatrix).invert()`, `Vector3f(1f,1f,1f)`, `Matrix4f(...)`, and `com.jme3.math.Vector3f`/`Quaternion` per bone per frame.
- `Ray.distanceToPoint` allocates up to three vectors per call (called per object in picking).
- `SkeletonMath` is allocation-free (good example).
- Render passes rebuild lists/matrices per frame in several `render*` methods.

Follow-ups: REN/ECS/PHY (P2) — hoist temporaries to fields (pattern already used in `RagdollSystem.tempVec*`); add a JFR/allocation profile of a 60 s editor session before optimising (QA can provide a harness; no GL here to measure).

## 6. Units and coordinate-system conventions

- No document states the convention. Observed: right-handed, Y-up (JOML default, Bullet default); `Transform` rotations are Euler **degrees** in the editor and converted to radians through `toRadiansF()` (`MathExtensions`); physics, cameras and `DayNight/Light` systems use a mixture of degrees and radians (`SpotLightComponent`, `DirectionalLightSystem`, `DayNightCycleSystem`, `CameraManager`).
- Physics uses SI (metres, kilograms, seconds) implicitly; `libbulletjme` margins are in metres.

Follow-ups: ECS (P1) — write the convention (Y-up, right-handed, metres, rotations stored in degrees at the component level, radians internally) in `docs/design/` and name fields with unit suffixes or KDoc; PHY/REN (P2) — audit each degrees↔radians call site; QA (P3) — add a few conversion round-trip unit tests per component once agreed.

## 7. Config and versioning

- Scene (`Serializer`), `AssetMeta` and `MaterialAsset` JSON use `ignoreUnknownKeys = true` and `encodeDefaults = true` but carry **no schema/format version**, so old files cannot be migrated and new fields silently drop on downgrade. `Project.version` is the *user's* project version, not a format version.
- Hard-coded developer paths remain: `ProjectWizardWindow.kt:92` (`C:\workspace\skate_workspace`), `game/GameMain.kt:57` (see BUG-011).
- `SearchHistory` writes `search_history.json` to the CWD (BUG-012); editor settings location is not centralised.
- Natives: dependencies are Windows-only; `build.gradle.kts` pins `libbulletjme` 22.0.3 through the version catalog (good).

Follow-ups: AST (P1) — add `formatVersion` to scene/asset/material files with a migration hook and a loader test; EDT (P2) — move wizard default and search history into the user-data directory; GPL (P2) — BUG-011; QA (P2) — add a round-trip test per versioned format.
