# QA-19 — Editor responsiveness audit

Request (human, Discord 2026-11-17): the editor is sometimes sluggish when creating a project or pressing Play. Rule 10:
heavy editor work runs off the UI thread with coroutines and progress; only GPU uploads and ImGui calls stay on the main thread.

## Method

- Read every editor path that does heavy work and noted the thread each step runs on (`LoadingRunner` steps,
  `JobSystem.runIO`/`runAsync`/`runOnMain`, direct calls).
- Measured the real code in `src/test/.../editor/responsiveness/EditorResponsivenessTimingTest.kt`: a real `ProjectManager`,
  `PrefabsGenerator`, `SceneManager`, `Serializer` and `KotlinScriptHost`. Only GPU, window and sound work is faked. Real
  texture (STB) and model (Assimp) decodes are timed for every asset a new project loads. Results go to
  `build/qa19-timings.txt`.
- Machine: the dev Windows box, JDK 17, run through `gradlew.bat` from WSL. Three runs; the table shows the range.
- Not measured: GPU uploads and shader compiles (no GL context headless), and the system reloads on Stop (physics
  rebuild etc.; the harness has no systems registered). Those need a manual profile in the real editor (see Questions).

What the user feels:

- **Create Project** stops the loading screen for the whole main step: 1.0–1.3 s of CPU work plus 0.6–0.8 s of real
  decodes (offender #2) ≈ **1.6–2 s with no frame drawn**, after the 1–2.6 s copy step that does draw.
- **Play** costs only about 0.1 s for the default scene. With a scene that has a Kotlin script active (the Feature
  Showcase has `[UI] SeedController`), the first Play of the session freezes the editor for **7–13 s**. Later Plays
  hit the memory cache. The cache is lost on every restart because the runtime host has no disk cache
  (`ScriptingSystem` builds `KotlinScriptHost()` without a `cacheDir`).
- **Opening a project or scene** pays offender #2 on the main step until the assets are cached.

## Offenders and proposed tasks (one per owning domain)

Suggested IDs. The lead assigns the final ones in `GameEngine.md`.

1. **SCR (P1) — Compile scripts off the main thread, with a disk cache.**
   - Do: `ScriptRuntime` asks the host to compile on a `JobSystem` worker and starts the script (`onCreate`) on the
     main thread when it is ready. Until then the script is pending and Play keeps drawing. Show "Compiling scripts…"
     in the status bar or viewport. Precompile the scripts of open scenes in the background on scene open and save,
     so Play hits the cache. Give the runtime host a `cacheDir` under the project's cache folder, so a restart stays
     warm. Hot reload during Play uses the same path.
   - Done when: the main thread never calls `KotlinScriptHost.load`/`reload`. A unit test with a fake host that
     blocks shows `ScriptRuntime.update` returning without waiting, and the script starting on a later frame.
   - Measured: 7–13 s cold, 0.45–0.77 s warm, today on the main thread.
2. **AST (P1) — Decode scene assets in the background, upload on main.**
   - Do: when a scene is opened (create, open project, open scene, Stop restore of an uncached scene), collect the
     model, texture and sound paths of the decoded scene in the background step. Decode them there through the
     existing `AssetLoadService` decode functions (`TextureLoader.decodeFromFile`, `AssimpLoader.importScene`). The
     main step only uploads, in per-frame batches with progress. Alternative: move `RenderComponent` and the
     environment sky to `requestModel`/`requestTexture` tickets with placeholders.
   - Done when: opening the new-project scenes runs no STB or Assimp decode on the main thread. A unit test with a
     fake loader records the decode thread.
   - Measured: 0.6–0.8 s per new project (`james.glb` 0.26–0.29 s, `sky_hdri.png` 0.2–0.34 s).
3. **EDT (P1) — Create Project: build the scenes off the main thread, and show copy progress.**
   - Do: split `ProjectManager.createProject` so generating, saving and decoding the default scenes happen in the
     background step. The main step only closes the old project and opens the decoded scenes (with #2, only the
     uploads remain). Report per-file progress in the copy step (now a single 1–2.6 s step). Also move the dirty-scene
     saves in `closeProject` behind the loading screen.
   - Done when: the main step of Create Project is under 100 ms with fake assets
     (`EditorResponsivenessTimingTest` can carry that budget once done).
   - Deps: GPL task 4.
4. **GPL (P2) — Prefab and showcase generation without GPU calls.**
   - Do: `PrefabsGenerator.createDefaultScenes`, `spawnDefaultsSync` and `FeatureShowcase.populate` call
     `assetsManager.getTexture`/`loadModel` while they build objects. They need path-only references, resolved
     when the scene opens, so generation is safe on a worker.
   - Done when: generation runs with an `AssetsManager` that throws on any load call (unit test).
5. **ECS (P3) — Write saved scenes in the background.**
   - Do: `SceneManager.saveScene` encodes on the main thread (the scene must not change while it is read) and writes
     the file on a worker. Report failures through the existing save result.
   - Measured: 28–52 ms for the showcase, growing with scene size.

Play capture and Stop restore stay on the main thread on purpose (they read and replace the live scene).
`EditorResponsivenessTimingTest` guards them with a 500 ms budget each (measured 27–78 ms; best of 5 runs).

## Guard added

`EditorResponsivenessTimingTest` (QA-19):

- Fails if Play capture or Stop decode of the new project's open scenes takes 500 ms or more (best of 5).
- Records every other timing above to stdout and `build/qa19-timings.txt`, so the owning tasks can show before/after
  numbers.
- The owning tasks above each add their own thread guard. A wall-clock budget on decodes or compiles would be flaky
  across machines.

## Questions for the human

1. When Play felt sluggish, which scene was active? With the Feature Showcase (or any scene with a script), the
   first Play of the session is the 7–13 s script compile (task 1). With `MainScene`, the measured CPU work is only
   about 0.1 s. The remaining cost would be GPU work (shader or pipeline compiles on the first Play frame) or the
   Stop/Play system reloads, which this headless audit cannot measure. A capture with the editor's frame-time overlay
   (or RenderDoc) on the first Play would settle it.
2. Is a short "Compiling scripts…" state at the start of Play (scripts start a few frames late) acceptable, or should
   Play wait behind a loading screen until scripts are ready?
